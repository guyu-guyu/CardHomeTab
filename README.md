# CardHomeTab

[中文](README.zh.md) · **English**

Turn one Markdown note into a start page. CardHomeTab splits that note by headings, renders every section as a card through Obsidian's own renderer, and lets each card carry its own CSS.

> The plugin interface (commands, settings, notices) is currently available in Chinese only.

## Features

- A home view with a logo (built-in Lucide icon, vault image or URL), a wordmark, and a background image with separate light/dark sources, blur and dimming.
- Fuzzy search over vault filenames, plus bookmarks and recent files. `Enter` opens the current tab, `Ctrl`/`Cmd`+`Enter` a new tab.
- Card content comes from a single dashboard note, split by a configurable heading level.
- Any content type renders, because rendering goes through Obsidian's `MarkdownRenderer`: plain text, fenced code, `query` blocks, `base` blocks, and `dataview`/`dataviewjs` blocks when Dataview is installed.
- Cards live in a real note, so `![[table.base]]`, `![[image.png]]` and relative links resolve against the dashboard note's folder.
- Per-card metadata in a native `%%card: %%` comment: CSS snippets, column span, and icon.
- Five built-in CSS snippets grouped by the content type they target, plus your own snippets from the snippets folder.
- Reorder cards by dragging; edit card bodies in the ordinary note editor.
- Works on desktop and mobile; public APIs only.
- Cards follow along while you edit the dashboard note in a tab.

## Installation

### Community plugins

In Obsidian, open **Settings → Community plugins → Browse** and search for "CardHomeTab". This works once the plugin has been listed in the community directory.

### Manual installation

1. Download `main.js`, `manifest.json` and `styles.css` from the latest release — or run `npm ci && npm run build` and take them from `dist/`.
2. Create `<Vault>/.obsidian/plugins/card-home-tab/` in your vault.
3. Copy the three files into that folder.
4. Reload Obsidian, then enable "CardHomeTab" under **Settings → Community plugins**.

`dist/` is a self-contained build output: every build cleans it and regenerates it, so its contents can be installed or published as-is.

## The dashboard note

The default dashboard file is `Home.md`. A heading whose level equals the **card heading level** (2 by default) starts a card; the card body runs until the next heading of that same level.

```markdown
# My home

## Stats
%%card: css=auto; span=2; icon=lucide-chart%%
- Files in the vault: `1,204`

## To-do
%%card: css=text,user:todo%%
- [ ] Review the release notes

### This H3 stays inside the card
## Another card starts here
```

- The H1 and the frontmatter are page-level and never become a card.
- Headings deeper than the card heading level render inside the card, as usual.
- The heading text is the card title.
- A section with no `%%card:` line is a plain card: `span=1`, no snippets, no icon.
- The note is an ordinary note. It opens, edits, searches, syncs and diffs like any other.

### The `%%card:` comment

The metadata line must be the first non-empty line after the heading.

```markdown
%%card: css=base; span=2; icon=lucide-chart%%
```

| Key | Value | Meaning |
| --- | --- | --- |
| `css` | comma-separated snippet references, or `auto` | CSS snippets applied to this card only |
| `span` | integer ≥ 1 | how many grid columns the card spans |
| `icon` | an Obsidian icon id, e.g. `lucide-chart` | icon shown before the card title |

Syntax rules:

- Fields are separated by `;`, multiple values by `,`, key and value by `=`.
- A reference without a source prefix means a built-in snippet: `css=base` is `css=builtin:base`.
- `auto` may be combined with explicit references: `css=auto,user:mine`.
- Unrecognised keys are preserved as written.
- `%% %%` is Obsidian's native comment syntax. It is hidden in reading mode and shown as dimmed text in Live Preview — that is Obsidian's behaviour, not extra markup added by the plugin.
- The whole line is generated by the card settings dialog and can equally be written by hand.

### `css=auto`

`css=auto` applies the built-in snippets that match the content types actually present in the card body:

- every fenced code block adds `builtin:code`;
- the fence language `base`, `query`, `dataview`, `dataviewjs` adds the matching snippet;
- an embed of a `.base` file (`![[table.base]]`) adds `builtin:base`;
- `builtin:text` always applies.

Detection reads the **source** — the fence languages and the `.base` embeds. It does not inspect the rendered DOM, so a `.base` embed produced by something else, or content a third-party plugin renders from inline syntax, is not detected. Snippets are applied in the order text, code, base, query, dataview.

## Built-in snippets

Built-in snippets are grouped by the **rendered content type** they target, not by visual style. They only do the cramped, awkward part — an embedded block inside a card — and leave the card's own look to your snippets.

| Snippet | Targets | What it does |
| --- | --- | --- |
| `builtin:text` | Markdown body | trims the first/last element margins, scales headings down, tightens list indentation and table borders |
| `builtin:code` | fenced code blocks, inline code | caps code blocks at 22em with inner scrolling; monospace font |
| `builtin:query` | ` ```query ` blocks | compacts the query header and result list, caps it at 24em with inner scrolling |
| `builtin:base` | ` ```base ` blocks and `![[…base]]` embeds | tightens margins, sticky table header, caps the view at 24em, shrinks the toolbar |
| `builtin:dataview` | ` ```dataview ` / ` ```dataviewjs ` | compact tables with a sticky header, tighter lists and tasks, smaller error box |

The `builtin:query` selectors are the internal ones (`.internal-query-header`, `.search-result-container`). Obsidian never emits a `.block-language-query` wrapper for query blocks, so styling them means styling their contents.

## How per-card CSS snippets work

- References are `builtin:name` or `user:name`. User snippets are read from `<config dir>/snippets/*.css` — the same folder Obsidian's own appearance settings use.
- Do **not** enable a card snippet in **Settings → Appearance → CSS snippets**: enabling it there applies it globally. The plugin reads the file itself and never touches `enabledCssSnippets`.
- The snippet source is wrapped in

  ```css
  @scope (.home-card.home-card[data-card-id="…"]) {
    /* your snippet, unchanged */
  }
  ```

  and attached to the document as a constructable stylesheet, so its rules can only match inside that one card. The scope class is repeated to lift specificity to `0,2,0`, so theme selectors do not win over your snippet.
- `:root` is rewritten to `:scope`. Inside `@scope`, `:root` still means the document root and would never match. Theme-prefixed selectors such as `.theme-dark .foo` keep working, because the theme class sits on `body`.
- Snippets may not use `@import`. Such a snippet is rejected, a warning is logged, and the card renders without it; the other snippets on that card still apply.
- Styles match the rendered DOM. Inside the scope:

  ```text
  .home-card[data-card-id]
  ├── .home-card-header        icon, title, hover action bar
  └── .home-card-content.markdown-rendered
      └── .home-card-content-inner
          └── rendered Markdown
  ```

  `markdown-rendered` is added to `.home-card-content` itself, so `.home-card-content.markdown-rendered p { … }` is the form that matches.

## Using the home view

Hover a card to reveal its action bar:

| Action | Behaviour |
| --- | --- |
| Drag handle | Moves the section in the dashboard note |
| Card settings | Dialog for icon, CSS snippets (built-in and user, multi-select) and column span; writes back to the `%%card:%%` line and re-renders that card |
| Edit | Opens the dashboard note with the cursor on that card's heading |
| Delete | Removes the section, after a confirmation |

Cards are rendered read-only on the home view; all writing happens in the note.

Commands (the interface is in Chinese):

| Command | Meaning |
| --- | --- |
| `打开首页` | Open the home view |
| `刷新所有卡片` | Re-render every card |
| `在标签页打开仪表盘` | Open the dashboard note in a tab |
| `新建卡片` | Append a new card section to the dashboard note |

## Settings

| Section | Settings |
| --- | --- |
| Page | Dashboard file (a text field with note completion, so a path that does not exist yet can be typed in), card heading level (H2–H6), grid columns (1–6), replace new tabs, open home on startup |
| Branding | Logo type (none / built-in icon / vault image / URL), icon id or image path, logo scale (0.2–5), logo colour (empty follows the theme accent; built-in icons only), wordmark text, show wordmark, wordmark font size, wordmark font weight (100–900) |
| Background | Background type (none / vault image / URL), light background, dark background (empty falls back to the light one), blur (0–40), dim (0–100) |
| Search | Show search bar, Markdown only, show path, show bookmarks, show recent files, max results (1–50), recent files count (0–20) |
| Snippets | The built-in and user snippets with their paths, the snippet folder, and a "refresh list" button |

## Known limitations

1. **One dashboard file.** There is a single dashboard note and no multi-dashboard switching.
2. **A card body cannot contain a heading of the same level** as the card heading level. Such a heading starts a new card. Deeper headings are fine.
3. **Mixed line endings.** `updateCardMeta` and `appendCard` always insert `\n`, so editing a CRLF dashboard note leaves the touched line with `\n` while the rest of the file keeps `\r\n`. Parsing is unaffected; the file just stops being uniformly CRLF on the line the plugin wrote.
4. **Settings are not indexed by Obsidian 1.13+'s settings search.** The tab is imperative (`display()`), which `minAppVersion` 1.9.0 requires, and `getSettingDefinitions()` returns an empty array, so 1.13+ shows the page but its settings are not searchable.
5. **A `%%card:` value cannot contain `;`** (the field separator), and a token without `=` is not representable. Rather than silently dropping what it cannot represent, the plugin refuses to rewrite such a line and tells you to fix it by hand.
6. **CSS snippets must not use `@import`.** Such a snippet is rejected and logged, and the card renders without it.
7. **`css=auto` only detects content from the source** — fenced code-block languages and `.base` embeds — not from the rendered DOM.
8. **Obsidian 1.9.0 or newer is required.** `@scope` needs Chromium 118+, and `base` blocks were introduced in 1.9.0, so `minAppVersion` is 1.9.0. All features use public APIs, which is why the plugin works on mobile.
9. **`builtin:dataview` has not been calibrated against a live Dataview install.** Its selectors come from Dataview's own stylesheet, but the elements Dataview actually wraps its blocks in were not confirmed in a vault with Dataview installed. If the compaction does not take effect, those selectors need adjusting against the real DOM.
10. **Non-goals.** Cards cannot be folded, nested or edited inline, and a card cannot live in its own file — a card is a section of the dashboard note and nothing more. The `%%card: %%` line is visible as dimmed text in Live Preview.
